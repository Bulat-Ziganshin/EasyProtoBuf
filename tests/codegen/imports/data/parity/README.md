# Step 11's two-way oracle parity corpus

Plan 4's refusals are settled against `protoc`, but the evidence used to be
per-finding and per-round, under a gitignored directory. This directory is the
standing table instead: **every diagnostic code the linker can emit gets a row,
and every row names both directions** — an input `protoc` accepts which the
linker must also accept (the row's *accept column*, without which a rule that
over-refuses passes every refusal-only fixture), and an input `protoc` refuses
which the linker must refuse with that code and no other.

The step's text is `plan4/steps/06-oracle-parity.md` in the execution pack; the
measurement this corpus was born from is
`build/plan4/oracle-parity/parity-verdicts.txt` (libprotoc 30.1, 26 cases).

## The two readers

| Reader | What it reads | Where it runs |
| --- | --- | --- |
| `tests/codegen/imports/test_parity.cpp` | every row, both link modes | CTest rows `codegen.imports.parity` (descriptor-origin rows; every profile) and `codegen.imports.parity.source` (source-origin rows; parser-on profiles) |
| `run.py --protoc <path>` | every row's `protoc` cell | opt-in, like the differential lane; it needs a `protoc` |

The lane is two CTest rows built from one file because the package's A12 split
makes "parser-free" and "parser-dependent" mutually exclusive target classes:
`verify-package.py`'s `iso:parser-free targets link nothing the parser owns`
fails any target that links `easypb_schema` alone in a parser-off tree and the
loader in a parser-on one. Each binary names every row it does not read with a
`SKIP:` line and the name of the binary that does — and because CTest prints a
passing test's output only under `-V`, a green run is not by itself evidence:
the step's log is taken from a verbose run, exactly as Step 8.3's differential
lane does.

## `parity-cases.tsv`

Six tab-separated columns, one header line:

| Column | Meaning |
| --- | --- |
| `case` | fixture stem (`source/<case>.proto`, `set/<case>.txtpb`, `set/<case>.pbs`) |
| `origin` | `source` or `descriptor` |
| `protoc` | `accept` or `reject` — the declared verdict, re-derived by `run.py` |
| `expected` | `accept`, or the `DiagnosticCode` enumerator the linker must answer with |
| `kind` | `pair`, `inverse` or `none` |
| `note` | the decision or the record, for `inverse`/`none`; empty for `pair` |

**Naming rule, and why it exists.** A row is named
`<origin-letter>-<slug>[-<discriminator>]-<direction>`, where `<origin-letter>`
is `s` or `d` and `<slug>` is the enumerator minus its `DIAGNOSTIC_` prefix,
lower-cased with `_` turned into `-`. That makes §11.1's accept column a
property of the DATA: for every row whose `expected` is a code, the row
`<origin-letter>-<slug>-accept` must exist with `expected = accept`, and both
readers check that rule against the tsv itself rather than carrying a second
table of the same facts. A row that loses its accept half therefore fails the
lane instead of passing quietly.

`kind` says which of the three legal shapes a row is: `pair` (both directions
exist and agree), `inverse` (`protoc` and the linker disagree **by decision**,
named in the note), or `none` (no counterpart can exist, reason in the note).

**Verdicts, never messages.** Nothing in this corpus asserts `protoc`'s wording
or ours. The project deliberately does not follow `protoc`'s sentences (E310,
W13/W14, B8/B9/B12/B14/B15): E1/A3 make the code, not the text, the contract. A
row that starts asserting message text is out of scope, in either reader.

## The two authoring forms, and the A13 protocol

`source/<case>.proto` is the fixture for a source-origin row; `source/` holds
every case root plus the shared dependencies (`dep.proto`, `sub/dep.proto`, the
cycle pair), so a case cannot pass because a sibling happened to redefine it.
The linker half reads these through the loader's own path; `run.py` compiles
them with one `--proto_path` invocation.

`set/<case>.txtpb` is the fixture for a descriptor-origin row and **is the
readable text**; `set/<case>.pbs` is the tracked binary the linker half decodes.
The bytes are `protoc`'s own encoding of the text:

```sh
protoc --proto_path=<dir with google/protobuf/descriptor.proto> \
       --encode=google.protobuf.FileDescriptorSet \
       google/protobuf/descriptor.proto < set/<case>.txtpb > set/<case>.pbs
protoc --descriptor_set_in=set/<case>.pbs --cpp_out=<empty dir> root.proto
```

The second command is protocol A13: **no `--proto_path` at all**, run from an
empty directory. With a proto path that holds the same `root.proto`, `protoc`
recompiles the source and never reads the set — the `D-24` counter-example.
`run.py --descriptor-proto-path <dir>` re-runs both halves of this protocol, so
a textproto and its tracked bytes cannot drift apart; without that argument the
re-encode is skipped **by name**.

The fixtures are generated by `build/plan4/step-11-oracle-parity/fixtures/
build_fixtures.py` (scratch, not tracked), whose `protoc-verdicts.txt` records
the measured `protoc` verdict of every case beside the first line it printed.

## What the linker half asserts, per row

* the declared verdict in **complete** mode, and, on a refusal,
  `DIAGNOSTIC_GENERIC` is never the answer and nothing is published (`A1`);
* the same verdict in **compatibility** mode wherever that mode can witness the
  row — a set of exactly one descriptor-origin file. Every other row cannot be
  witnessed by that mode at all: A26's precondition refuses a set of any other
  shape *before* the index, resolution or the finish pass runs, so what is
  asserted there is that refusal (`DIAGNOSTIC_GENERIC`, nothing published). A
  mode precondition is not a parity verdict, and the difference is asserted
  rather than papered over;
* a source-origin row the **loader** itself refuses (the import classes decided
  before any link) is asserted at that stage, with the code the loader answered
  with: a mode is a property of a link that happened.

Nothing is asserted about message text.

## Rows that are deliberately not parity

* **`d-generic-not-raised` — `none`.** `DIAGNOSTIC_GENERIC` is not a parity code:
  its value is `0`, it is the bucket for the loader/CLI classes the plan does not
  classify, and it is what an accept leaves untouched. The row is the *negative*
  one — an accepted graph must never come back `GENERIC` — and the linker half
  asserts that table-wide: **no row may be refused with `GENERIC` in complete
  mode**, and the only `GENERIC` refusals anywhere are compatibility mode's own
  precondition, counted and checked against the rows that mode cannot witness.
* **`d-unsupported-syntax-editions-inverse` — `inverse`.** `protoc` 30.1 accepts
  its own encoding of `edition = "2023";` — which carries **both**
  `syntax: "editions"` and `edition: EDITION_2023` (measured) — and this project
  refuses it by A25, because the model carries no editions semantics and
  `classify_file_syntax` (`codegen/schema.cpp`) is keyed on the syntax string.
  A descriptor carrying only the `edition` enum and no syntax string is accepted
  by **both** readers, which is parity, not a divergence; that is why the fixture
  is spelled the way `protoc` writes it.
* **`d-invalid-import-public-index-duplicate-inverse` and
  `d-invalid-import-public-and-weak-inverse` — `inverse`.** `protoc` accepts a
  repeated `public_dependency` index and an index that is both public and weak;
  `bind_import_edges` refuses both by A18 (the pack's tolerance table rejects an
  index that repeats a `dependency`; `allow_missing` relaxes missing *targets*
  only). Ledger `D-29`, closed as a recorded decision on 2026-09-27 and pinned
  by `test_bind_rejects_duplicate_and_overlapping_indexes`. Neither shape can be
  witnessed in compatibility mode — both need a second file — so the pair has no
  compat half by construction.
* **Three fixtures carry no row: `source/probe-source-{proto3,proto4,
  editions}.proto`.** Measured: the source frontend refuses `syntax = "proto4"`
  (`syntax must be "proto2" or "proto3"`) and `edition = "2023"` (`expected a
  top-level .proto statement`) itself, as a **parse error carrying
  `DIAGNOSTIC_GENERIC`**, so `DIAGNOSTIC_UNSUPPORTED_SYNTAX` is unreachable from
  `.proto` text and the code's rows live at the descriptor origin, where
  `schema_linker.cpp` owns it. A row may not name `GENERIC` (the bucket is not a
  verdict), so the shapes are kept as evidence rather than as rows — but they
  are **not the same relation**, measured 2026-09-28: `syntax = "proto4"` is
  parity (`protoc` refuses it as source text too, and both answers are the
  bucket because a file the parser refused is never classified), while
  `edition = "2023";` is an **inverse** on this origin as well as on the
  descriptor one — `libprotoc 30.1` ACCEPTS it and models the file as
  `syntax: "editions"`, our parser refuses it, and that refusal is A25's
  recorded capability boundary (owned by plan 5), not a parity verdict.

## Provenance of every cell

`protoc` column: measured with **libprotoc 30.1** (`C:/Base/Tools/BIN/protoc.exe`),
recorded per case with the first line protoc printed in
`build/plan4/oracle-parity/parity-verdicts.txt` and re-derived on every run of
`run.py`, which prints `protoc --version` first. That version is **this lane's
arbiter**. The differential lane under `tests/codegen/parser/differential/` pins
a different one (libprotoc 3.13.0) for the parser corpus; the two are named and
scoped rather than competing, and CI provisions neither (see the step's notes
for the recorded decision).
